## 시험지 조판에서 가장 어려운 건?

<Layout.Center>

문항 배치가 아니라 **문항 분할**이다.

</Layout.Center>

<Notes>
  시험지 조판에서 가장 어려운 게 뭘까요? 문항을 배치하는 건 쉽습니다. 높이 재고,
  단에 맞게 넣으면 됩니다. 어려운 건 문항을 '자르는' 겁니다. 문항이 단 높이보다
  길면 어디선가 잘라서 다음 단으로 넘겨야 하는데, 아무 데서나 자르면 안 됩니다.
</Notes>

---

## 자르면 안 되는 곳들

<Steps>

- ❌ 수식 중간
- ❌ 문제 번호 직후 (번호만 덩그러니)
- ❌ 이미지 중간
- ❌ 보기 묶음 중간

</Steps>

<Notes>
  수식이 반으로 갈라지면 안 됩니다. 문제 번호만 왼쪽 단에 남아도 안 됩니다.
  보기가 두 단에 흩어지면 학생이 헷갈립니다. 이런 제약 조건들을 지키면서 공간
  효율도 챙겨야 합니다. 생각보다 복잡한 문제입니다.
</Notes>

---

## `column-count: 2`로 충분할까?

<Steps>

- 어디서 잘릴지 예측 불가
- 미리보기 구현 어려움
- 브라우저마다 결과 다름
- 세밀한 제어 불가

</Steps>

→ 직접 만들어야 한다

<Notes>
  CSS의 column-count를 쓰면 될 것 같지만, 한계가 있습니다. 어디서 잘릴지 예측할
  수 없어서 미리보기를 정확하게 보여줄 수 없습니다. 결국 직접 만들어야 합니다.
  그래서 브라우저가 이 문제를 어떻게 푸는지 들여다봤습니다.
</Notes>

## 옛날 방식: 다 그리고, 가위로 자르기

```
레이아웃 단계: 길게 쭉 그림 (분할 모름)
     ↓
페인팅 단계: 좌표 조작해서 잘린 척
```

<Notes>
  크롬의 옛날 렌더링 엔진은 단순했습니다. 콘텐츠를 세로로 길게 쭉 그린 다음,
  화면에 보여줄 때 일정 간격으로 잘린 것처럼 좌표를 조작했습니다. 레이아웃
  단계에서는 분할을 모르고, 페인팅 단계에서 분할을 흉내 내는 겁니다.
</Notes>

---

## 레이아웃 ≠ 페인팅 → 버그

<Steps>

- `box-shadow`가 단 경계에서 뚝 잘림
- `transform` 적용하면 위치가 엉망
- 스크롤 영역이 두 단에 걸치면 좌표계 붕괴

</Steps>

<Notes>
  이 방식은 많은 버그를 낳았습니다. 그림자가 단 경계에서 끊기고, 회전 효과를
  주면 요소가 엉뚱한 데 나타났습니다. 레이아웃은 '하나의 긴 조각'으로 계산하고,
  페인팅은 '여러 조각인 척'하니까 둘 사이에 간극이 생긴 겁니다.
</Notes>

## LayoutNG의 핵심 아이디어

**2022년, Chrome 102**

<Layout.Center>

> "다 그리고 자르지 말고,
> **나누면서 그려라**"

</Layout.Center>

<Notes>
  2022년에 도입된 LayoutNG는 접근법을 완전히 바꿨습니다. 핵심 아이디어는
  하나입니다. "다 그리고 자르지 말고, 나누면서 그려라." 이사할 때 짐을 바닥에
  늘어놓고 가위로 자르는 사람은 없잖아요. 박스를 앞에 두고 하나씩 담습니다.
  브라우저도 이제 이렇게 합니다.
</Notes>

---

## 첫 번째 단 끝, 두 번째 단 시작

"150px에서 멈췄다" — 이걸로 충분할까?

```
문항 3
├─ 문제 번호 "3."
├─ 지문
│  ├─ 첫 번째 문단
│  ├─ 밑줄 친 부분 ← 여기 중간에서 잘림
│  └─ 두 번째 문단
└─ 보기 (1) (2) (3) (4) (5)
```

<Notes>
  그런데 문제가 있습니다. 첫 번째 단을 채우고 두 번째 단을 시작할 때, 어디서부터
  이어야 할까요? "150픽셀에서 멈췄다"만으로는 부족합니다. 문항 안에 지문이 있고,
  지문 안에 밑줄 친 부분이 있는데, 그 중간에서 잘렸다면 어떨까요? 굉장히 많은
  정보가 필요합니다.
</Notes>

---

## Break Token: 트리 구조의 책갈피

```typescript
문항의 Break Token
├─ consumed: 200px
├─ borderDrawn: true
└─ children:
   └─ 지문의 Break Token
      ├─ consumed: 150px
      └─ children:
         └─ 밑줄 부분의 Break Token
            └─ consumed: 40px
```

<Notes>
  그래서 브라우저는 '책갈피'를 만듭니다. Blink에서는 이걸 Break Token이라고
  부릅니다. 중요한 건 이게 단순한 숫자가 아니라 트리 구조라는 점입니다. HTML이
  트리이듯, Break Token도 트리입니다. 문항의 Break Token 안에 지문의 Break
  Token이 있고, 그 안에 밑줄 부분의 Break Token이 있습니다. 각각 "여기까지
  그렸다", "테두리는 이미 그렸다" 같은 정보를 담고 있습니다.
</Notes>

---

## Break Token에 기록되는 것들

| 필드          | 의미                          |
| ------------- | ----------------------------- |
| `consumed`    | 이 요소에서 소비한 높이       |
| `sequence`    | 몇 번째 조각인가 (0, 1, 2...) |
| `borderDrawn` | 상단 테두리를 이미 그렸는가   |
| `children`    | 자식 요소들의 Break Token     |

<Notes>
  Break Token에는 이런 정보들이 들어갑니다. consumed는 해당 요소에서 얼마나
  소비했는지, sequence는 이게 몇 번째 조각인지, borderDrawn은 테두리를 이미
  그렸는지. 그리고 children에 자식 요소들의 Break Token이 중첩됩니다. 이 구조
  덕분에 아무리 깊이 중첩된 요소라도 정확히 이어서 그릴 수 있습니다.
</Notes>

## Break Appeal: 분할 위치의 점수

| 등급 | 위치                | 예시                      |
| ---- | ------------------- | ------------------------- |
| 최고 | 자연스러운 경계     | 문항 사이, 보기 사이      |
| 보통 | orphans/widows 위반 | 첫 줄만 남김              |
| 나쁨 | avoid 규칙 위반     | `break-after: avoid` 직후 |
| 최악 | 분할 불가           | 수식 중간, 이미지 중간    |

<Notes>
  모든 위치가 동등하지 않습니다. 브라우저는 각 위치에 점수를 매깁니다. 이걸
  Break Appeal이라고 부릅니다. 문항 사이처럼 자연스러운 경계는 최고점입니다.
  문제 번호 직후처럼 번호만 고립되는 위치는 점수가 낮습니다. 수식 중간은 아예
  불가능입니다.
</Notes>

---

## 되돌림 (Relayout)

```
지문 끝 도달 → 선택지가 안 들어감 → 분할 필요
         ↓
그런데 "지문 다음에서 분할 금지" 규칙이 있다면?
         ↓
더 나은 위치로 되돌아가서 다시 배치
```

**제약: 단당 최대 1회**

<Notes>
  배치하다가 나쁜 분할 위치를 만나면 어떻게 할까요? 브라우저는 지나온 분할
  지점들을 기록해둡니다. 더 나은 곳이 있으면 거기까지 되돌아가서 다시
  배치합니다. 이걸 relayout이라고 합니다. 다만 중요한 제약이 있습니다. 되돌림은
  단당 최대 한 번만 허용됩니다.
</Notes>

---

## 왜 한 번만?

무제한 되돌림의 위험:

<Steps>

- 무한 루프 가능성
- 연산량 급증 → 성능 저하

</Steps>

<Layout.Center>

> "완벽한 결과보다
> **예측 가능한 동작**이 더 중요하다"

</Layout.Center>

<Notes>
  왜 한 번만 허용할까요? 무제한 되돌림은 두 가지 위험이 있습니다. 분할 제약
  조건들이 상충하면 무한 루프에 빠질 수 있고, 되돌림이 많아질수록 성능이 급격히
  나빠집니다. LayoutNG의 설계 철학은 명확합니다. 완벽한 결과보다 예측 가능한
  동작이 더 중요하다.
</Notes>

---

## Monolithic 요소

**절대 자르면 안 되는 것들**

<Steps>

- 이미지
- 수식
- 표
- 스크롤 영역

</Steps>

단 높이보다 크면? → **넘치게 둔다**

<Notes>
  수식이나 이미지처럼 절대 자르면 안 되는 요소가 있습니다. 이걸 Monolithic
  요소라고 부릅니다. 이런 요소가 단 높이보다 크면 어떻게 할까요? 브라우저는
  자르지 않고 그냥 넘치게 둡니다. 단 밖으로 삐져나오게 놔둡니다.
</Notes>

# 시험지 조판에 적용하기

## 브라우저 방식을 그대로 쓸 수 없는 이유

| 브라우저        | 시험지                       |
| --------------- | ---------------------------- |
| 넘침 허용       | 넘침 = 겹침 = 치명적         |
| 단 높이 고정    | 페이지별 조정 필요할 수도    |
| 미리보기 불필요 | 미리보기 필수                |
| 범용 콘텐츠     | 문항 번호, 배점 등 특수 요소 |

<Notes>
  브라우저 방식을 그대로 쓸 수는 없습니다. 브라우저는 넘침을 허용하지만,
  시험지에서 넘치면 다음 문항과 겹칩니다. 치명적입니다. 미리보기도 필수고, 문항
  번호나 배점 같은 특수 요소도 처리해야 합니다.
</Notes>

---

## 브라우저에게 배운 핵심 원칙

<Steps>

1. **나누면서 배치한다** - 다 그리고 자르지 않음
2. **책갈피를 트리로 관리한다** - 중첩 구조 정확히 추적
3. **분할 위치에 점수를 매긴다** - 문항 사이 > 보기 사이 > 문단 내
4. **되돌림에 제한을 둔다** - 무한 루프 방지
5. **자를 수 없는 건 인정한다** - 수식, 이미지는 통째로 넘김

</Steps>

<Notes>
  그래도 핵심 원칙은 그대로 가져왔습니다. 나누면서 배치한다. 책갈피를 트리로
  관리한다. 분할 위치에 점수를 매긴다. 되돌림에 제한을 둔다. 자를 수 없는 건
  인정한다. 이 다섯 가지입니다.
</Notes>

---

## 추가로 고려한 것들

<Steps>

- **높이 측정**: 렌더링해봐야 안다 → 캐싱
- **Monolithic 초과**: 넘치게 두지 않고 통째로 다음 단으로
- **단 균형**: 마지막 페이지 양쪽 단 높이 맞추기
- **강제 분할**: "이 문항은 새 페이지에서 시작"

</Steps>

<Notes>
  추가로 고려한 것들이 있습니다. 텍스트 높이는 렌더링해봐야 아는데, 문항이 수백
  개면 측정만으로 몇 초가 걸립니다. 그래서 캐싱을 도입했습니다. Monolithic
  요소가 단보다 크면 넘치게 두지 않고 통째로 다음 단으로 넘겼습니다. 마지막
  페이지의 단 균형 맞추기도 필요했고, "이 문항은 새 페이지에서 시작"같은 강제
  분할도 지원해야 했습니다.
</Notes>

## Break Token 구조 예시

```typescript
interface BreakToken {
  questionIndex: number;
  blockIndex: number;
  consumedHeight: number;
  borderDrawn: boolean;
  childToken?: BreakToken;
}
```

<Notes>
  실제 코드에서 Break Token은 이런 식으로 구현했습니다. questionIndex는 몇 번째
  문항인지, blockIndex는 문항 내 몇 번째 블록인지, consumedHeight는 얼마나
  소비했는지. 그리고 childToken으로 자식의 Break Token을 중첩합니다.
</Notes>

---

## 정리

**콘텐츠 분할 = 어디서 자를 것인가**

브라우저의 해법:

<Steps>

- 배치와 분할의 통합
- Break Token (트리 구조의 책갈피)
- Break Appeal (분할 위치 점수)
- 제한된 되돌림

</Steps>

→ 에디터의 여러 문제에 적용 가능 (페이지 나눔, 인쇄, 가상화 등)

<Notes>
  정리하겠습니다. 콘텐츠 분할의 핵심은 "어디서 자를 것인가"입니다. 브라우저는
  배치와 분할을 통합하고, Break Token으로 상태를 관리하고, Break Appeal로 좋은
  위치를 찾고, 되돌림에 제한을 둡니다. 이 원칙들은 시험지 조판뿐 아니라 페이지
  나눔, 인쇄, 가상화 등 에디터의 여러 문제에 적용할 수 있습니다.
</Notes>
