## 0.0 이 책에 대하여

### 무엇을 만드나요?

이 책에서는 **웹 기반 스프레드시트 애플리케이션**을 처음부터 만들어갑니다. Google Sheets나 Excel Online처럼 브라우저에서 작동하며, 수만 개의 셀을 부드럽게 다룰 수 있는 애플리케이션입니다.

```
최종 모습:
┌─────────────────────────────────────────────────┐
│  File  Edit  View  Insert  Format  Data  Help  │
├─────┬──────────┬──────────┬──────────┬──────────┤
│     │    A     │    B     │    C     │    D     │
├─────┼──────────┼──────────┼──────────┼──────────┤
│  1  │  Name    │   Age    │  Status  │  Score   │
├─────┼──────────┼──────────┼──────────┼──────────┤
│  2  │  Alice   │    30    │  Active  │    95    │
├─────┼──────────┼──────────┼──────────┼──────────┤
│  3  │  Bob     │    25    │ Inactive │    82    │
└─────┴──────────┴──────────┴──────────┴──────────┘
```

완성된 스프레드시트는 다음 기능을 제공합니다:

- 수만 행의 데이터를 부드럽게 스크롤
- 셀 선택, 편집, 포맷팅
- 방향키, Tab, Enter로 이동
- 수식 계산 (=SUM, =AVERAGE 등)
- Undo와 Redo
- 복사와 붙여넣기

### 왜 스프레드시트를 만드나요?

스프레드시트는 겉으로는 단순해 보이지만, 내부적으로는 여러 복잡한 문제를 다룹니다. 렌더링 성능, 상태 관리, 키보드 인터랙션, 수식 계산 등 모던 웹 애플리케이션이 직면하는 거의 모든 도전 과제가 이 안에 담겨 있습니다.

프론트엔드 개발 관점에서 스프레드시트는 다음을 경험할 수 있는 이상적인 프로젝트입니다:

**기술적 도전**:

- 대규모 데이터셋을 다루는 성능 최적화
- 복잡한 사용자 인터랙션 처리
- 예측 가능한 상태 관리
- 접근성을 고려한 키보드 네비게이션

**소프트웨어 설계**:

- 명확한 관심사의 분리
- 테스트 가능한 아키텍처
- 확장 가능한 컴포넌트 구조
- 의존성 관리

**알고리즘과 자료구조**:

- 의존성 그래프를 통한 수식 계산
- 효율적인 데이터 구조 선택
- 메모이제이션과 캐싱
- 명령 패턴을 통한 실행 취소

### 이 책의 대상 독자

이 책은 다음 지식을 가진 개발자를 위해 쓰였습니다:

**필요한 배경**:

- JavaScript와 TypeScript의 기본 문법
- React Hooks (useState, useEffect, useRef)
- HTML과 CSS 기초
- npm이나 yarn 같은 패키지 매니저 사용 경험

**얻게 될 것**:

- Test-Driven Development의 실전 경험
- 성능 최적화 기법과 virtualization
- 복잡한 UI를 구조화하는 방법
- 대규모 프로젝트를 관리하는 패턴

중급 개발자가 고급 수준으로 성장하는 데 필요한 실무 경험을 제공하는 것이 이 책의 목표입니다.

## 0.1 Test-Driven Development

### 개념의 이해

Test-Driven Development(TDD)는 코드를 작성하기 전에 테스트를 먼저 작성하는 개발 방법론입니다. 이는 단순한 테스트 작성 순서의 변경이 아니라, 소프트웨어 설계에 대한 근본적으로 다른 접근입니다.

```
전통적 개발 흐름:
구현 → 동작 확인 → 버그 발견 → 수정 → 반복

TDD 흐름:
테스트 작성 → 실패 확인 → 구현 → 통과 확인 → 리팩토링
```

### Red-Green-Refactor 사이클

TDD는 세 단계의 반복적인 사이클로 진행됩니다:

**🔴 Red (실패하는 테스트)**

먼저 원하는 동작을 설명하는 테스트를 작성합니다:

```typescript
// Cell.test.tsx
it('should render with text value', () => {
  render(<Cell value="Hello" />);
  expect(screen.getByText('Hello')).toBeInTheDocument();
});
```

이 시점에서 `Cell` 컴포넌트는 존재하지 않으므로 테스트는 실패합니다. 이 실패는 예상된 것이며, 테스트가 올바르게 작성되었음을 확인해줍니다.

**🟢 Green (최소한의 구현)**

테스트를 통과시키는 가장 간단한 코드를 작성합니다:

```typescript
// Cell.tsx
export function Cell({ value }) {
  return <div>{value}</div>;
}
```

테스트가 통과합니다. 이제 올바르게 동작하는 코드가 생겼습니다.

**🔵 Refactor (개선)**

테스트가 통과하는 상태를 유지하면서 코드를 개선합니다:

```typescript
// Cell.tsx
export function Cell({ value }: { value: string | number }) {
  return (
    <div className="cell" style={{ padding: '8px' }}>
      {value}
    </div>
  );
}
```

테스트는 여전히 통과합니다. 리팩토링 과정에서 실수로 기능을 망가뜨리지 않았음을 테스트가 보장해줍니다.

### TDD의 가치

전통적인 개발에서는 코드를 먼저 작성하고 나중에 테스트를 추가합니다. 이 경우 다음과 같은 문제가 발생할 수 있습니다:

```typescript
// 코드를 먼저 작성
function calculateTotal(items) {
  let total = 0;
  for (let item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

// 나중에 발견되는 엣지 케이스들:
// - items가 빈 배열이면?
// - item.price가 undefined면?
// - quantity가 음수면?
```

TDD 접근에서는 이러한 엣지 케이스를 미리 고려하게 됩니다:

```typescript
// 1. 테스트가 엣지 케이스를 먼저 정의
describe('calculateTotal', () => {
  it('should return 0 for empty array', () => {
    expect(calculateTotal([])).toBe(0);
  });
  
  it('should handle missing price', () => {
    expect(calculateTotal([{ quantity: 2 }])).toBe(0);
  });
  
  it('should calculate correct total', () => {
    expect(calculateTotal([
      { price: 10, quantity: 2 },
      { price: 5, quantity: 3 }
    ])).toBe(35);
  });
});

// 2. 구현이 모든 케이스를 처리
function calculateTotal(items = []) {
  return items.reduce((total, item) => {
    const price = item.price ?? 0;
    const quantity = item.quantity ?? 0;
    return total + (price * quantity);
  }, 0);
}
```

TDD는 다음과 같은 이점을 제공합니다:

- 버그가 프로덕션에 도달하기 전에 발견됩니다
- 리팩토링 시 회귀(regression)를 방지합니다
- 테스트 자체가 코드 사용법을 문서화합니다
- 테스트하기 쉬운 코드는 일반적으로 더 나은 설계를 가집니다

### 이 책에서의 적용

모든 챕터는 일관된 패턴을 따릅니다:

```
1. 기능 소개와 개념 설명
2. 테스트 작성 (Red)
3. 최소한의 구현 (Green)
4. 코드 개선 (Refactor)
5. 브라우저에서 동작 확인
6. 다음 기능으로 이동
```

처음에는 테스트를 먼저 작성하는 것이 어색하게 느껴질 수 있습니다. 이는 자연스러운 과정입니다. 몇 개의 챕터를 진행하면서 TDD의 리듬이 몸에 익게 됩니다.

## 0.2 개발 환경

### 필요한 도구

프로젝트는 다음 도구들을 사용합니다:

**필수 도구**:

- Node.js 18 이상
- npm 또는 yarn
- 코드 에디터 (VS Code 권장)

**권장 도구**:

- Git (버전 관리)
- Chrome 또는 Firefox (DevTools)

### Node.js 버전 확인

터미널은 현재 설치된 Node.js 버전을 표시합니다:

```bash
node --version
# v18.0.0 이상이어야 합니다

npm --version
# 9.0.0 이상이어야 합니다
```

버전이 요구사항을 충족하지 않는다면, [Node.js 공식 사이트](https://nodejs.org/)에서 LTS 버전을 다운로드할 수 있습니다. 설치 후 터미널을 재시작하면 새 버전이 적용됩니다.

### VS Code 확장 프로그램

VS Code는 다음 확장 프로그램과 함께 사용할 때 개발 경험이 크게 향상됩니다:

- **ESLint** - 코드 품질 문제를 즉시 표시합니다
- **Prettier** - 일관된 코드 스타일을 자동으로 적용합니다
- **Vitest** - 테스트 결과를 에디터 안에서 확인할 수 있습니다
- **Error Lens** - 에러와 경고를 해당 줄에 인라인으로 표시합니다

확장 프로그램은 `Ctrl+Shift+X` (Mac: `Cmd+Shift+X`)를 눌러 설치할 수 있습니다.

## 0.3 프로젝트 생성

### Vite 프로젝트 초기화

Vite는 빠른 개발 서버와 최적화된 빌드를 제공하는 프론트엔드 빌드 도구입니다. 새 프로젝트는 다음 명령으로 생성됩니다:

```bash
npm create vite@latest spreadsheet-app -- --template react-ts
```

이 명령은 React와 TypeScript로 구성된 프로젝트를 생성합니다. 프롬프트가 나타나면 프로젝트 이름과 템플릿을 확인하고 진행합니다.

### 의존성 설치

프로젝트 폴더로 이동한 후:

```bash
cd spreadsheet-app
npm install
```

npm은 필요한 모든 패키지를 다운로드하고 설치합니다. 이 과정은 네트워크 속도에 따라 몇 분 정도 소요될 수 있습니다.

### 개발 서버 실행

```bash
npm run dev
```

개발 서버가 시작되면 브라우저에서 `http://localhost:5173`을 열어볼 수 있습니다. Vite 기본 페이지가 표시되면 프로젝트가 올바르게 설정된 것입니다.

### 테스트 도구 설치

TDD를 위해서는 테스트 프레임워크와 관련 라이브러리가 필요합니다:

```bash
npm install -D vitest @testing-library/react @testing-library/jest-dom @testing-library/user-event jsdom @vitest/ui
```

각 패키지의 역할:

- **vitest** - 빠른 테스트 실행 환경을 제공합니다
- **@testing-library/react** - React 컴포넌트를 테스트하는 유틸리티입니다
- **@testing-library/jest-dom** - DOM 상태를 검증하는 매처를 추가합니다
- **@testing-library/user-event** - 사용자 인터랙션을 시뮬레이션합니다
- **jsdom** - Node.js 환경에서 브라우저 DOM을 시뮬레이션합니다
- **@vitest/ui** - 테스트 결과를 웹 인터페이스로 확인할 수 있게 합니다

## 0.4 Vitest 설정

### 설정 파일 구조

Vitest는 프로젝트 루트의 `vitest.config.ts` 파일을 통해 설정됩니다:

```typescript
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';
import path from 'path';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: './src/test/setup.ts',
    coverage: {
      provider: 'v8',
      reporter: ['text', 'json', 'html'],
      exclude: [
        'node_modules/',
        'src/test/',
        '**/*.test.{ts,tsx}',
        '**/*.config.{ts,js}',
      ],
    },
  },
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src'),
    },
  },
});
```

이 설정은 다음을 지정합니다:

- `environment: 'jsdom'` - 브라우저 환경을 시뮬레이션합니다
- `globals: true` - describe, it, expect 같은 함수를 전역에서 사용할 수 있게 합니다
- `setupFiles` - 각 테스트 실행 전에 필요한 설정을 불러옵니다
- `coverage` - 코드 커버리지 측정 방식을 정의합니다

### 테스트 초기화 설정

`src/test/setup.ts` 파일은 모든 테스트가 실행되기 전에 필요한 설정을 준비합니다:

```typescript
import { expect, afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';
import * as matchers from '@testing-library/jest-dom/matchers';

expect.extend(matchers);

afterEach(() => {
  cleanup();
});

globalThis.requestAnimationFrame = (cb: FrameRequestCallback) => {
  return setTimeout(cb, 0) as unknown as number;
};

globalThis.cancelAnimationFrame = (id: number) => {
  clearTimeout(id);
};
```

이 설정의 의미:

- `expect.extend(matchers)` - toBeInTheDocument 같은 DOM 매처를 추가합니다
- `afterEach(cleanup)` - 각 테스트 후 렌더링된 컴포넌트를 정리합니다
- `requestAnimationFrame` 모킹 - 애니메이션 API를 테스트 환경에서 사용할 수 있게 합니다

### TypeScript 설정

`tsconfig.json`의 `compilerOptions`에 다음 설정이 필요합니다:

```json
{
  "compilerOptions": {
    "types": ["vite/client", "vitest/globals", "@testing-library/jest-dom"],
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

이는 TypeScript가 테스트 관련 타입을 인식하고, `@/` 경로 별칭을 사용할 수 있게 합니다.

### 스크립트 추가

`package.json`의 scripts 섹션은 자주 사용하는 명령을 단축키로 제공합니다:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc && vite build",
    "preview": "vite preview",
    "test": "vitest",
    "test:ui": "vitest --ui",
    "test:coverage": "vitest --coverage"
  }
}
```

각 스크립트의 역할:

- `npm test` - watch 모드로 테스트를 실행합니다. 파일이 변경되면 자동으로 재실행됩니다
- `npm run test:ui` - 웹 브라우저에서 테스트 결과를 시각적으로 확인합니다
- `npm run test:coverage` - 코드 커버리지를 측정하고 리포트를 생성합니다

## 0.5 첫 번째 테스트

### 간단한 함수와 테스트

설정이 올바른지 확인하기 위해 간단한 유틸리티 함수와 테스트를 작성합니다.

`src/utils/math.ts` 파일을 만듭니다:

```typescript
export function add(a: number, b: number): number {
```

## 0.7 코드 품질

### ESLint 설정

ESLint는 코드 작성 중에 잠재적인 문제를 발견합니다. `eslint.config.js` 파일은 프로젝트의 린팅 규칙을 정의합니다:

```javascript
import js from '@eslint/js'
import globals from 'globals'
import reactHooks from 'eslint-plugin-react-hooks'
import reactRefresh from 'eslint-plugin-react-refresh'
import tseslint from 'typescript-eslint'
import { defineConfig, globalIgnores } from 'eslint/config'
  
export default defineConfig([
  globalIgnores(['dist']),
  {
	files: ['**/*.{ts,tsx}'],
	extends: [
	  js.configs.recommended,
	  tseslint.configs.recommended,
	  reactHooks.configs.flat.recommended,
	  reactRefresh.configs.vite,
	],
	languageOptions: {
	  ecmaVersion: 2020,
	  globals: globals.browser,
	},
	rules: {
	  'react-refresh/only-export-components': [
	    'warn',
	    { allowConstantExport: true },
	  ],
	  '@typescript-eslint/no-explicit-any': 'warn',
	  '@typescript-eslint/no-unused-vars': [
		'error',
		{
		  argsIgnorePattern: '^_',
		  varsIgnorePattern: '^_',
	    },
	  ],
	},
  },
])
```

이 규칙들은 일반적인 실수를 방지하고 일관된 코드 스타일을 유지하는 데 도움을 줍니다.

### Prettier 설정

Prettier는 코드를 자동으로 포맷팅합니다. `.prettierrc.json` 파일이 스타일을 정의합니다:

```json
{
  "semi": true,
  "trailingComma": "es5",
  "singleQuote": true,
  "printWidth": 80,
  "tabWidth": 2,
  "useTabs": false,
  "arrowParens": "always",
  "endOfLine": "lf"
}
```

VS Code에서 `Shift+Alt(Option)+F`를 누르면 현재 파일이 자동으로 포맷팅됩니다.

### 린트와 포맷 스크립트

`package.json`에 다음 스크립트를 추가하면 전체 프로젝트를 검사하고 포맷팅할 수 있습니다:

```json
{
  "scripts": {
    "lint": "eslint . --ext ts,tsx --report-unused-disable-directives --max-warnings 0",
    "format": "prettier --write \"src/**/*.{ts,tsx,css}\""
  }
}
```

`npm run lint`는 문제를 발견하고, `npm run format`은 코드 스타일을 일관되게 만듭니다.

## 0.9 개발 워크플로우

### 일상적인 개발 흐름

개발은 일반적으로 두 개의 터미널 프로세스를 동시에 실행하며 진행됩니다.

첫 번째 터미널에서 개발 서버를 실행합니다:

```bash
npm run dev
```

브라우저는 `http://localhost:5173`에서 애플리케이션을 보여줍니다. 파일을 수정하면 브라우저가 자동으로 업데이트됩니다.

두 번째 터미널에서 테스트를 watch 모드로 실행합니다:

```bash
npm test
```

파일이 변경되면 관련 테스트가 자동으로 재실행됩니다. 이를 통해 코드 변경이 기존 기능을 망가뜨리지 않았는지 즉시 확인할 수 있습니다.

### TDD 워크플로우 예시

새 기능을 추가할 때는 다음 순서를 따릅니다:

```bash
# 새 기능 브랜치 생성
git checkout -b feature/cell-selection

# 1. 테스트 작성 (Red)
#    src/components/__tests__/Cell.test.tsx 수정
#    테스트 실행 - 실패 확인 ❌

# 2. 구현 (Green)
#    src/components/Cell.tsx 수정
#    테스트 실행 - 통과 확인 ✅

# 3. 리팩토링
#    코드 개선하되 테스트는 계속 통과 유지

# 4. 커밋
git add .
git commit -m "feat: Add cell selection"
```

이 사이클은 각 기능마다 반복됩니다.

특정 테스트만 실행하고 싶을 때는 `.only`를 사용합니다:

```typescript
it.only('should test this specific case', () => {
  // 다른 테스트는 건너뛰고 이 테스트만 실행됩니다
});
```

나중에 작성할 테스트는 `.skip`으로 표시할 수 있습니다:

```typescript
it.skip('should implement later', () => {
  // 이 테스트는 건너뜁니다
});
```

테스트 디버깅이 필요하면 `console.log`를 사용합니다. 출력은 터미널에 표시됩니다.

## 0.13 문제 해결

### 일반적인 문제들

**"Cannot find module" 에러가 발생하는 경우**

의존성이 제대로 설치되지 않았을 수 있습니다. node_modules 폴더를 삭제하고 다시 설치합니다:

```bash
rm -rf node_modules
npm install
```

**TypeScript가 'describe'를 인식하지 못하는 경우**

`tsconfig.json`의 types 설정을 확인합니다:

```json
{
  "compilerOptions": {
    "types": ["vitest/globals"]
  }
}
```

**테스트가 자동으로 재실행되지 않는 경우**

watch 모드가 활성화되어 있는지 확인합니다:

```bash
npm test -- --watch
```

**포트가 이미 사용 중이라는 메시지가 나타나는 경우**

다른 포트를 지정해서 실행합니다:

```bash
npm run dev -- --port 3000
```

다음 챕터에서는 첫 번째 컴포넌트를 만들기 시작합니다. 가장 작은 단위인 Cell 컴포넌트부터 시작해서, Row와 Grid로 확장해나갑니다.

두 개의 터미널을 준비합니다:

```bash
# 첫 번째 터미널: 개발 서버
npm run dev

# 두 번째 터미널: 테스트
npm test
```

### 진행 방식

각 챕터는 다음 흐름을 따릅니다:

1. 개념 소개 - 무엇을 만들고 왜 만드는지 설명합니다
2. 테스트 작성 - 원하는 동작을 테스트로 먼저 표현합니다
3. 구현 - 테스트를 통과시키는 코드를 작성합니다
4. 개선 - 테스트가 통과하는 상태를 유지하며 코드를 다듬습니다
5. 확인 - 브라우저에서 실제 동작을 확인합니다

처음에는 테스트를 먼저 작성하는 것이 어색할 수 있습니다. 이는 자연스러운 과정입니다. 몇 개의 기능을 만들다 보면 TDD의 리듬이 익숙해집니다.

코드를 작성하고, 테스트를 실행하고, 브라우저에서 확인하는 이 순환을 즐기시기 바랍니다. Chapter 1에서 만나요.
